# Dong Skill · 懂 Skill

**让听众能够真正懂你的报告。懂？懂！**

![Dong Skill V1：把问题、动机、方法、证据和讨论连成听得懂的讲解](docs/images/dong-skill-hero.png)

**V1 · v1.0.0** ｜ 报告审核与完整修订 ｜ 演讲稿生成

Dong Skill 是一个面向论文讲解、科研进展和工作汇报的 Codex skill。它站在**没有实际参与底层工作**的听众视角，检查报告的概念、组织与证据，让听众知道：你在解决什么问题，为什么这样做，实验回答了什么，结论又能走多远。

## V1 能做什么

| 任务 | 交付 |
| --- | --- |
| 审核已有报告 | 有位置、有原因、有替换内容的具体修改建议 + 完整修改版 |
| 审核已有演讲稿 | 具体修改建议 + 完整修订稿，并核对与报告是否一致 |
| 根据报告、论文或可靠材料生成演讲稿 | 可直接口播的完整稿件 + 时长估算，必要时附问答备查 |

V1 的生成功能仅针对演讲稿，暂不从零生成完整报告。基于已有报告进行重组、修订并交付完整修改版，属于审核流程。

## “懂”的七个标准

| 标准 | 具体怎么做 |
| --- | --- |
| **总分总** | 开头讲清整份报告的逻辑，各部分展开，结尾回收问题与结论。开头不能只是念目录。 |
| **同层级对仗** | 同级标题和并列说法保持一致的概念维度、抽象层次与句式。 |
| **论文五段主线** | Field & Task → Motivation → Method → Result → Discussion。工作汇报按目标与任务适配。 |
| **正文与 Appendix 分工** | 正文讲清机制和关键证据；实现细节、配置、完整数据放入可检索的附录。 |
| **真实 case** | 使用来源可追溯、容易理解的实际案例，说明输入、处理、实际结果和对应启示。 |
| **实验回应动机** | 检查每个核心问题是否有方法设计、验证实验和相称结论，区分效果、机制与泛化。 |
| **听众视角** | 清理内部编号、隐含背景和项目黑话，让未参与工作的人也能跟上。 |

例如：材料已确认 `SFT-210` 是所比较的 SFT 基座时，正文、图表和口播统一使用 **“SFT 基座”**，原始编号留在 Appendix 中追溯。如果存在多个基座，就依据实际设置清楚区分。数字本身影响结论时保留并解释，例如“训练至第 210 步”；不能猜测编号含义，也不能删掉后缀后混淆不同实验。

## 安装

将本仓库克隆到 Codex 的个人 skills 目录，目录名保持为 `dong-skill`：

```bash
mkdir -p "${CODEX_HOME:-$HOME/.codex}/skills"
git clone https://github.com/SowingG2333/dong-skill.git \
  "${CODEX_HOME:-$HOME/.codex}/skills/dong-skill"
```

需要固定使用 V1 时，在该目录检出发布标签：

```bash
git -C "${CODEX_HOME:-$HOME/.codex}/skills/dong-skill" checkout v1.0.0
```

也可下载 [V1 发布包](https://github.com/SowingG2333/dong-skill/releases/tag/v1.0.0)，将其中的 `dong-skill/` 文件夹放进上述 skills 目录。入口为 [SKILL.md](SKILL.md)。

## 使用

附上报告、论文或稿件，然后在请求中使用 `$dong-skill`。

**审核报告**

```text
请使用 $dong-skill 审核这份报告。
听众了解该领域，但没有参与这项工作的实现和实验。
请给出具体修改建议及完整修改版，重点检查逻辑链、
实验能否回答 Motivation、真实 case 和正文/Appendix 的分工。
```

**生成演讲稿**

```text
请使用 $dong-skill 根据这份报告生成一篇约 15 分钟的中文演讲稿。
开头先讲逻辑，主体解释机制与关键证据，结尾总结。
请与报告章节对应，Appendix 用作问答备查，不逐项念出。
```

**审核演讲稿**

```text
请使用 $dong-skill 对照报告审核这份演讲稿。
检查数字、结论、术语和语义名称是否一致，
给出具体修改建议与完整修订稿，并估算口播时长。
```

提供听众背景、用途、目标时长和可用原始证据，会使结果更贴近实际需要。已有足够信息时，skill 会直接处理。

## 审核交付长什么样

审核默认交付三部分：

1. **具体修改建议**：定位到章节、原文片段或图表，说明问题、影响、具体改法和替换内容；复杂科研主张附问题—实验对应表。
2. **完整修改版**：落实建议，保留开头、主体、总结与 Appendix 的分工，覆盖全部已提供内容。
3. **仍待补充或核验的项目**：明确缺少什么、补在哪里、影响什么结论；没有则省略。

没有真实 case、关键数据或验证实验时，会明确标注待补，并使用现有证据允许的表述。不会把设想写成已完成实验，也不会用编造案例把稿件补成“完整”。

## 仓库结构

```text
dong-skill/
├── SKILL.md                 # V1 入口、范围与共同标准
├── agents/openai.yaml       # Codex 显示信息与调用提示
├── references/
│   ├── review.md            # 审核、建议与完整修订
│   └── speech.md            # 口播稿生成、审核与时长
├── docs/
│   ├── images/              # README 原创生成插图
│   └── image-prompts.md     # 插图提示词与生成方式
└── CHANGELOG.md             # 发布记录
```

本仓库包含通用规则与原创生成插图。用于设计规则的私人报告、演讲稿、截图、项目数据及其具体分析笔记均不随仓库发布。图中卡片和图形是装饰性示意，不代表实际研究结果。
